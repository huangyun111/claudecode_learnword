# 2026-11-10 · 当系统出错，责任为什么总在接口处消失：技术伦理与责任链

> 模块 H12 · 道德判断、责任与技术伦理 ｜ 标签：technology ethics, AI accountability, responsibility chain, lifecycle governance, procurement, human oversight, incident response, remedy, auditability, traceability
> 主线：技术系统的伤害很少由一个按钮独立造成。目标、数据、模型、供应商合同、部署情境、组织激励、人工复核和申诉渠道共同塑造结果。责任链不是把所有错误压给程序员或最后点击的人，而是沿 authority、control、knowledge、benefit、capacity 与 duty，把预防、说明、停止、调查、补偿和修复分配给真正有能力履行的主体，并让交接处保留证据与升级通道。

---

## ⏮ 上篇回顾（30 秒）

上一篇用 care ethics 说明：技术是否“帮助了人”，不能只看 efficiency，还要看需要是否被看见、照护是否有能力、接受者能否回应，以及负担转移给了谁。

今天把 H12-2 的 moral responsibility 与 H12-3 的关系责任接进完整技术生命周期。问题不再只是“谁犯了错”，而是：**谁本来应该预防，谁必须说明，谁有权停止，谁负责修复，受影响者又怎样得到实际 remedy？**

## 🎬 开篇：医院说是模型建议，供应商说是医生决定

一家医院购买了急诊分诊模型。某天，系统把一名症状不典型的患者评为低风险，患者等待过久后病情恶化。

调查时，每个环节都能给出一句看似合理的话：

- 数据团队：“训练数据是医院提供的。”
- 供应商：“产品只是 decision support，不替代医生。”
- 医院采购：“系统通过了合同中的 accuracy 指标。”
- 科室管理者：“医生始终可以 override。”
- 值班医生：“每小时几百名患者，没有时间逐项核查。”
- IT 部门：“我们只负责接入，不负责临床流程。”
- 监管部门：“尚未收到正式 incident report。”

最后，责任仿佛在每一次交接中变薄，直到没人拥有完整问题。

但患者受到的伤害是完整的。要避免“many hands 变成 no hands”，必须把系统当作一条社会技术链，而不是一个孤立模型。

## 第一层：Technology Ethics 不只是给模型贴原则标签

“公平、透明、可靠、以人为本”都重要，但原则本身不会自动分配工作。

例如“系统应公平”至少还要回答：

1. 对谁、在哪个决策和哪个比较维度上公平？
2. 谁负责识别受影响群体？
3. 谁能取得 subgroup data？
4. 谁设定 acceptable harm threshold？
5. 谁拥有暂停上线的权力？
6. 发生伤害后，谁通知、调查、补偿并修改流程？

所以可以区分：

- **Ethical principle**：什么价值应被保护；
- **Responsibility allocation**：谁在何时负责什么；
- **Accountability mechanism**：他必须向谁说明，证据怎样被检查；
- **Liability**：法律在特定管辖和事实下怎样分配后果；
- **Remedy**：受影响者如何获得纠正、恢复、赔偿或其他补救。

伦理不能代替法律，法律也不会自动覆盖所有组织性失责。责任链的作用，是把抽象价值变成可执行、可留痕、可复核的制度动作。

## 第二层：责任不应平均分，要沿六个维度分配

面对复杂系统，可以先问六个问题。

### 1. Authority：谁有决定权

谁能定义目标、批准数据、选择模型、签合同、上线、改变 threshold、暂停系统或提供补救？有权而不承担对应义务，会制造责任空洞。

### 2. Control：谁能实际改变结果

形式上“可以 override”不等于实质控制。还要看是否有信息、时间、工具、权限和不受惩罚的空间。

### 3. Knowledge：谁知道或应当知道风险

开发者知道模型限制，部署者知道本地情境，一线人员知道 workflow，受影响者知道自己的生活后果。责任设计要让这些知识能够汇合和上行。

### 4. Benefit：谁从系统中获益

谁获得利润、效率、预算节省或组织声誉？将收益集中、风险外包给一线或公众，通常是不稳定的安排。

### 5. Capacity：谁有能力履责

把 monitoring 交给没有日志、预算或专业人员的部门，只是在纸面上分配责任。

### 6. Duty：谁因角色、承诺或法律负有特别义务

供应商、采购方、部署机构、专业人员与监管者的 duty 不同。角色责任可以并存，不必只找一个“最终罪人”。

因此责任不是平均切蛋糕，而是让 **权力、知识、能力、收益与义务相匹配**。

## 第三层：Design——先问是否该建，而不只是怎样建

技术项目最早的伦理决定，常发生在写第一行代码之前。

需要明确：

- legitimate purpose 是什么；
- 不用 AI 是否有更简单、更可解释、更少侵入的方案；
- 谁会受到收益与伤害；
- 哪些错误不可接受；
- 哪些用途明确排除；
- 何时应当停止项目。

“我们能预测什么”不能替代“我们有理由据此决定什么”。例如模型能预测员工离职概率，不等于雇主就有正当理由秘密监控、惩罚高风险员工。

这一步的责任通常属于 product owner、业务机构、领域专家和治理层，而不只是 machine-learning engineer。因为 objective function 之前，已经有人选择了问题、对象和权力关系。

## 第四层：Data——数据不是过去事实的无辜镜子

数据责任至少包含：

1. **Origin**：数据从哪里来，是否有合法与正当依据；
2. **Coverage**：哪些群体、情境和失败模式缺失；
3. **Label**：标签由谁定义，是否把制度偏差写成 ground truth；
4. **Proxy**：变量是否代理了受保护属性或资源差异；
5. **Temporal validity**：旧数据是否仍代表新环境；
6. **Access / deletion**：谁能使用、保留、纠正和删除；
7. **Feedback**：模型上线后是否改变了未来训练数据。

例如“过去被批准贷款”不等于“过去真正有偿还能力的人”。若历史决策本身受信息、制度与偏见影响，训练模型可能是在复制旧分配，而不是发现自然规律。

数据团队负责 provenance、quality 与 limitation；业务与领域团队负责判断 label 是否有规范意义；治理层负责确认收集和使用的目的是否正当。任何一方都不能独自完成。

## 第五层：Model 与 Evaluation——平均准确率不是上线许可证

模型评价要从 benchmark 进入 decision context。

至少要检查：

- false positive / false negative 各伤害谁；
- subgroup 与 worst-case 是否可接受；
- confidence 是否校准；
- distribution shift 与 adversarial / misuse 风险；
- latency、missing input、fallback 和 security；
- 与现有流程相比，系统是否真的改善结果；
- threshold 是谁根据什么价值权衡决定的。

这里有一个常被忽略的边界：

> 模型团队可以报告 performance trade-off，却不能独自决定哪类人的哪种错误“值得承受”。

threshold selection 同时是技术和制度决定，需要领域人员、受影响群体、管理者以及必要时的法律 / 伦理审查共同参与。

## 第六层：Procurement——买来的系统不会把责任一并外包

很多组织并不自己训练模型，而是采购 API、软件或整体服务。风险因此集中在合同接口：

- 供应商只给 aggregate benchmark；
- 买方不知道训练数据与 intended use；
- 日志、版本、subgroup test 和 incident information 无法取得；
- 模型更新无需重新验收；
- 合同结束后无法迁移数据或继续维护；
- 发生伤害时双方互相指向对方。

负责任采购至少要把以下内容写进 requirement 和 contract：

1. intended use 与 prohibited use；
2. data / model provenance 和已知限制；
3. 本地 validation 与 acceptance criteria；
4. version change、retesting 和通知义务；
5. logging、audit access 与 evidence retention；
6. security、privacy 与 incident reporting；
7. support、training、knowledge transfer 与 exit plan；
8. 谁负责 suspend、investigate、notify 与 remedy；
9. 违约、损害和保险等风险怎样分配。

供应商应对其可控制的技术、文档与质量负责；部署机构仍要对本地用途、workflow、人员和最终服务负责。采购不是责任转移，而是责任接口设计。

## 第七层：Deployment——同一个模型进入新场景，就成了新系统

模型在测试集上合格，不等于部署系统合格。部署会新增：

- 本地 population 与 base rate；
- 新的输入设备与 missingness；
- UI 默认项和 warning 方式；
- 工作量、绩效考核与 automation bias；
- 与旧流程、人员和其他系统的 interaction；
- 用户可能的 adaptation、gaming 与 over-reliance。

所以 deployer 需要做 context-specific impact assessment，并预设：

- 谁能使用输出；
- 输出只是建议、排序还是自动决定；
- 哪些 case 必须人工升级；
- 什么信息向 operator 与受影响者显示；
- 什么条件触发 fallback 或 suspend；
- 如何接收 complaint 与 appeal。

“产品说明书说可以用于医疗”不能替代医院自己的 validation；“用户点了同意”也不能替代组织对高风险 workflow 的责任。

## 第八层：Human Oversight 为什么常常只是责任装饰

一个人坐在环路里，不代表人真正控制系统。有效 oversight 至少需要：

1. **Competence**：理解系统能力、限制和 failure mode；
2. **Information**：看到原始证据、confidence、缺失数据和理由；
3. **Time**：有足够时间核查，而非高速点击；
4. **Authority**：能 override、暂停或升级；
5. **Support**：有替代流程、专家和资源；
6. **Protection**：提出风险不会被绩效惩罚；
7. **Feedback**：override 与 failure 会回到 monitoring 和改进流程。

若 operator 每小时处理几百个 case、只能看到一个红绿灯、推翻系统会降低 KPI，那么他可能只是 **moral crumple zone**：平时缺乏控制，出事后却承受全部责备。

好的 oversight 不是“机器决定，人来背书”，而是把真实权力和能力放进人机接口。

## 第九层：Monitoring——上线不是伦理审查的终点

模型进入现实后，风险会随时间变化：

- population 与 policy 变了；
- users 学会绕过系统；
- supplier 更新模型；
- 数据 pipeline 漂移；
- 原本少见的 failure 在规模化后累积；
- 一次局部 workaround 变成长期制度惯例。

监测不应只看 uptime 和 aggregate accuracy，还要看：

- subgroup / worst-case outcome；
- override、appeal 与 reversal；
- near miss、complaint 与 qualitative harm；
- input drift、calibration 与 missingness；
- workload、skill erosion 与 operator behavior；
- 谁没有进入数据，因为他已被系统排除。

还要预先设定 trigger：什么时候继续、降级、回滚、暂停或下线。没有 threshold 和 decision owner 的 dashboard，只是观看风险，不是治理风险。

## 第十层：Incident——先保护人，再保全证据，再追原因

OECD 将已经直接或间接导致实际伤害的事件区分为 AI incident，把可能导致此类伤害的事件称为 AI hazard。这个区分提醒我们：不应等到伤害落地才学习。

一个成熟的 incident response 至少包括：

~~~text
detect / report
  -> protect affected people and contain ongoing risk
  -> preserve logs, versions, inputs and decision records
  -> notify responsible internal and external actors
  -> investigate technical + organizational causes
  -> provide correction / appeal / compensation / support
  -> patch data, model, UI, workflow, contract and governance
  -> verify effectiveness and share lessons
~~~

不能为了“快速修 bug”而先覆盖关键日志；也不能为了等待完美因果结论而不采取临时保护。调查要同时看：

- proximal technical failure；
- 为什么测试没有发现；
- 为什么 warning 没有上行；
- KPI、资源和合同怎样塑造行为；
- 谁本可以暂停却没有权限或激励；
- 相似 case 是否仍在发生。

责任的目标不只是找到一个人，而是阻止伤害继续并修复造成它的整条链。

## 第十一层：Remedy 不是发一封道歉邮件

对受影响者而言，“模型已经改进”并不会自动修复过去的后果。Remedy 可能包括：

- 通知本人发生了什么；
- 允许访问并纠正相关数据；
- 提供可理解的理由；
- 由有权人员重新审查决定；
- 恢复资格、服务、记录或机会；
- 赔偿经济、身体或尊严损害；
- 提供医疗、法律、心理或其他支持；
- 对同类历史 case 做批量回查；
- 公开必要信息，防止重复伤害。

有效 remedy 还要求容易找到、负担可承受、时限合理，并且申诉不会带来报复。若受影响者必须先证明一个黑箱内部怎样出错，救济实际上就不可达。

## 第十二层：Decommissioning——系统停止使用后，责任仍未结束

技术生命周期还有最后一段：

- 数据和日志保留多久，谁能访问；
- 未决申诉和 incident 由谁继续处理；
- supplier 退出后如何迁移；
- 下线模型是否仍嵌在其他 workflow；
- 历史决定是否需要复核；
- deletion、archive 与 audit evidence 如何平衡。

“项目结束”不能成为清空责任的按钮。退出计划应在采购和部署前就写好，而不是供应商离场时临时补。

## 一张责任链地图：不同主体分别不能缺什么

| 主体 | 不可缺少的责任 |
|---|---|
| 产品 / 业务负责人 | 正当目的、替代方案、风险边界、go / no-go 与资源 |
| 数据团队 | provenance、quality、coverage、label limitation、access 与更新 |
| 模型团队 | performance、uncertainty、failure mode、reproducibility 与文档 |
| 供应商 | intended use、限制、版本、support、日志接口、incident cooperation |
| 采购方 | 本地需求、合同权利、audit access、exit 与风险分配 |
| 部署机构 | context validation、workflow、人员、最终决定、complaint 与 remedy |
| 一线 operator | 按程序使用、记录异常、在真实权限内 override / escalate |
| 治理 / 审计 | 独立检查、利益冲突控制、threshold 与持续 monitoring |
| 监管 / 司法 / 社会监督 | 最低规则、调查、执行、权利保护与外部救济 |
| 受影响者 | 不是风险承担者；应有知情、参与、质疑、申诉和补救渠道 |

注意最后一行：受影响者当然可以提供反馈和知识，但不能因此被要求负责发现、证明并修复系统伤害。

## 🌍 与当下的连接：从“可信 AI”口号转向可检查接口

近年的 AI 治理框架逐渐把重点从单次伦理宣言转向 lifecycle evidence：

- NIST AI RMF 用 Govern、Map、Measure、Manage 组织持续风险管理；
- GAO 以 governance、data、performance、monitoring 形成审计框架；
- UNESCO 强调 human responsibility、impact assessment、auditability、traceability 与 redress；
- 欧盟 AI Act 按角色和风险设置 provider / deployer 等义务，并对部分高风险使用要求 human oversight、post-market monitoring、impact assessment 与 serious-incident reporting；
- 公共采购指南开始要求把 data、audit、support、monitoring、liability 与 end-of-life 写进合同。

这些制度并不完全相同，也不能机械套用到所有场景。但共同趋势很清楚：

> 责任不能只存在于组织口号里，必须落到角色、文档、日志、阈值、权限、报告、申诉和补救接口上。

## 一张可复用的“技术责任十八问卡”

1. **Purpose**：系统解决什么问题，目的正当吗？
2. **Alternative**：不用 AI 或降低自动化是否更合适？
3. **Affected**：谁获益，谁承担错误和监控成本？
4. **Authority**：谁定义目标、批准上线、改变阈值和停止系统？
5. **Data**：来源、标签、缺失、代表性和更新如何？
6. **Model**：哪些 failure mode 已知，confidence 是否校准？
7. **Context**：部署人群、base rate、设备和 workflow 与测试有何不同？
8. **Supplier**：合同是否给出 provenance、日志、版本和 audit access？
9. **Acceptance**：什么证据满足上线，什么情况必须 no-go？
10. **Human**：人工是否有信息、时间、能力、权限和保护？
11. **Fallback**：系统不可用、低置信或冲突时怎么办？
12. **Monitor**：监测哪些 subgroup、outcome、complaint、near miss 与 drift？
13. **Trigger**：什么阈值触发降级、回滚、暂停或下线？
14. **Incident**：谁接收报告、保护人、保全证据并通知相关方？
15. **Investigation**：是否同时检查技术、组织、合同和激励原因？
16. **Remedy**：受影响者能否获得通知、复核、纠正、恢复和补偿？
17. **Learning**：修复是否覆盖同类历史 case，并验证没有制造新伤害？
18. **Exit**：系统和供应商退出后，数据、申诉、日志与义务归谁？

## 四种常见误解

### “模型只是工具，所以责任全在使用者”

工具的设计、已知限制、默认设置和供应商信息会塑造使用；使用者也有本地验证和流程责任。责任可分层并存，不必二选一。

### “有 Human in the Loop，就完成了问责”

若人没有信息、时间、权限、支持和免受报复的 override，环路只是形式。最后点击不等于拥有完整控制。

### “通过一次审计，就证明系统持续可信”

模型、数据、环境、用户和组织都会变化。一次 audit 是时间截面，不能替代 post-deployment monitoring、incident learning 和 change management。

### “事故修好模型就结束了”

修补未来 performance 不会自动纠正历史决定，也不会补偿已经发生的损害。技术修复与 person-facing remedy 都需要完成。

## 💬 谈资点 / 反常识洞见

1. **责任最容易消失的地方，不在代码内部，而在组织交接接口。**
2. **谁最后点击，不一定是谁最有权改变风险。**
3. **采购 AI 不是购买一个模型，而是购买一条长期信息与责任关系。**
4. **Human in the loop 有时不是安全设计，而是组织的责任缓冲垫。**
5. **平均准确率回答“模型多常对”，不回答“错时谁受伤、能否补救”。**
6. **Incident 是已发生的伤害，hazard 是可能造成伤害的信号；成熟组织会从 near miss 学习。**
7. **Auditability 不是公开所有源代码，而是让相关主张、过程和决定有足够证据可查。**
8. **供应商掌握技术知识，部署者掌握本地情境；任何一方单独负责都会有盲区。**
9. **有效监督的核心是权力，不只是屏幕前坐着一个人。**
10. **Remedy 是系统质量的一部分，因为不可纠正的错误会把全部不确定性压给个人。**
11. **下线也是治理动作：没有 exit plan，旧模型可能继续藏在流程里。**
12. **问责不是寻找替罪羊，而是让预防、解释、停止、修复都有人有能力完成。**

## 可靠来源

- [NIST AI Risk Management Framework 1.0](https://airc.nist.gov/airmf-resources/airmf/5-sec-core/)：以 Govern、Map、Measure、Manage 组织跨生命周期风险治理，并把 post-deployment monitoring、appeal、override、incident response、recovery 与 decommissioning 纳入 Manage。
- [U.S. GAO AI Accountability Framework](https://www.gao.gov/products/gao-21-519sp)：围绕 governance、data、performance 与 monitoring 提供机构、审计者和第三方评估者可检查的问题与证据。
- [UNESCO Recommendation on the Ethics of Artificial Intelligence](https://www.unesco.org/en/legal-affairs/recommendation-ethics-artificial-intelligence)：强调 AI 生命周期中的 human responsibility、impact assessment、auditability、traceability、oversight 与 redress。
- [OECD AI Incidents and Hazards Monitor Methodology](https://oecd.ai/en/incidents-methodology)：区分已经导致实际伤害的 AI incident 与可能导致伤害的 AI hazard，并推动可比较的事件学习。
- [EU Artificial Intelligence Act — Consolidated Text](https://eur-lex.europa.eu/eli/reg/2024/1689)：按系统风险和 operator role 设置义务；其中部分高风险场景涉及 provider / deployer、human oversight、fundamental-rights impact assessment、post-market monitoring 与 serious-incident reporting。
- [UK Guidelines for AI Procurement](https://www.gov.uk/government/publications/guidelines-for-ai-procurement/guidelines-for-ai-procurement)：把 impact assessment、data、go / no-go、供应商沟通、audit、ongoing monitoring、risk allocation、knowledge transfer 与 end-of-life 接入公共采购。
- [UK Data and AI Ethics Framework](https://www.gov.uk/government/publications/data-ethics-framework/data-and-ai-ethics-framework)：进一步说明使用第三方系统时，供应商责任应进入合同，而公共机构仍对 algorithm-assisted decisions 及其影响承担责任。

## 一句话总结

技术伦理不是在模型上线前做一次价值宣言，而是把正当目的、数据、模型、采购、部署、人工监督、监测、事故、补救和退出连成责任链：沿 authority、control、knowledge、benefit、capacity 与 duty 分配义务，在每个交接处保留日志、权限和升级通道，并让受影响者能够质疑、纠正和获得实际 remedy，才能避免 many hands 最终变成 no hands。
